# v1.0 真实架构 PRD (双引擎与 AI 灾备)

WeightHelper v1.0 版本的后端实现（基于 Node.js/Express 的 `server.js`）是一套高度解耦、抗脆弱性极强的系统。本 PRD 记录了当前已在生产环境稳定运行的核心业务逻辑。

## 1. 智能双引擎数据库架构 (Dual-Engine Database)

为了最大化开源项目的传播属性和开发便利性，后端抛弃了单一数据库绑定的死板设计，实现了一套极其精妙的自动适配架构。

### 1.1 环境自适应逻辑
在 `server.js` 启动瞬间，系统会执行嗅探逻辑：`const isPostgres = !!process.env.DATABASE_URL;`
*   **本地开发环境**：当未检测到该环境变量时，系统自动退化使用内置的 **SQLite**（`database.sqlite`）。开发者 Clone 代码后，无需安装任何数据库软件，一条命令即可启动。
*   **云端生产环境**：当部署到 Render 或其他 PaaS 平台并配置了 `DATABASE_URL` 时，系统自动挂载到云端 **PostgreSQL** 数据库。这彻底解决了 Render 免费实例因虚拟文件系统重启而导致 SQLite 数据丢失的致命 Bug。

### 1.2 统一适配器防线
*   **业务逻辑解耦**：所有的 CRUD 操作必须统一通过 `dbRun`、`dbGet`、`dbInsertAndGetId` 三个自定义函数执行。
*   **占位符安全转换**：业务层统一使用 `?` 作为参数占位符。若底层检测为 PostgreSQL，适配器内部会自动将其转换为 PG 格式的 `$1, $2, $3`。
*   **⚠️ 强约束规则**：绝对禁止在 SQL 语句中手动编写 `$1` 或 `$2`。这会触发适配器的双重替换逻辑，导致查询灾难。
*   **别名映射规范**：因为 PostgreSQL 会自动将未加双引号的列名（如 `foodName`）转换为小写（`foodname`），从而引发前端取值报错。目前的解决方案要求在 `GET /api/meals` 中强制添加别名映射：`foodname as "foodName"`。

## 2. 瀑布流 AI 模型灾备机制 (AI Disaster Recovery)

鉴于开源项目强依赖个人申请的 Google Gemini 免费 API Key，配额耗尽（429 报错）或某个特定版本模型下线（404 报错）是常态。必须建立灾备防线。

### 2.1 降级重试瀑布流
系统实现了一个名为 `generateWithFallback` 的核心控制器。当主模型遭遇请求限制或找不到模型时，它会按照以下顺序依次重试，直至拿到结果：
1.  `gemini-3.1-flash-lite`（优先使用最高版本的 Lite 模型，响应最快，容错最高）
2.  `gemini-3.5-flash`（高性能高计算力模型备用）
3.  `gemini-3.0-flash`
4.  `gemini-2.5-flash`
5.  `gemini-2.5-flash-lite`（绝对兜底防线）

### 2.2 核心解析 API (`POST /api/analyze`)
*   **功能**：接收前端传来的 base64 图片数据，调度灾备模型池进行视觉解析。
*   **鉴权拦截**：`authenticateToken` 中间件已被提升至路由最前方，确保只有携带有效 Token 的家庭成员才能触发昂贵的 AI 调用，且精准消耗该用户的 Token 额度。

## 3. 跨越半球的时区转换逻辑 (Chronobiological Pipeline)

为了解决长辈在北京、小辈在纽约的时区错乱问题，数据写入和读取必须经过严格的清洗。

### 3.1 用户设置层
*   **核心配置**：`users` 表中存储了两个核心字段：`goal`（每日卡路里目标）和 `timezone`（时区设置，如 `Asia/Shanghai`）。这两个偏好已从 `localStorage` 全面迁移至云端数据库（`GET/PUT /api/user/preferences`）。

### 3.2 数据查询层 (`GET /api/meals`)
*   **前端请求**：前端必须携带目标查询日期和当前用户的时区（例如 `?date=2026-06-05&tz=Asia/Shanghai`）。
*   **后端计算**：后端引入 `moment-timezone` 库，将前端传来的日期字符串当做指定时区的起点。计算出该时区当天的绝对时间戳区间（UTC 毫秒），然后去数据库中比对 `createdAt` 字段。这确保了查询结果的绝对正确，且与服务器部署在哪个国家（服务器时区）毫无关系。
