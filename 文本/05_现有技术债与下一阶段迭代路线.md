# 现有技术债与下一阶段迭代路线

当前的 v1.0 版本虽然已经跑通了跨国协同和 AI 自动灾备的核心闭环，但在基础设施层面仍存在明显的局限性。根据现有的知识库和代码库，我们梳理出了明确的技术债务与下一步迭代路线。

## 1. 最紧迫的体验阻塞：Render 冷启动问题

### 1.1 痛点描述
目前项目部署在 Render 平台的免费实例上。按照该平台的调度机制，在 15 分钟没有任何网络请求后，实例会自动进入休眠状态。当家庭成员试图吃午餐打卡时，首次打开 App 会面临长达 **30-50 秒的严重冷启动延迟**，这会导致极差的使用体验甚至请求超时。

### 1.2 下一步修复计划 (Sprint 1)
*   **短期干预**：引入第三方监控保活服务。配置 UptimeRobot（免费版），设定每 10 分钟向特定的 `/api/health` 探针路由发送一次 GET 请求，强制保持 Render 实例处于活跃状态，彻底消灭 50 秒的物理休眠唤醒时间。
*   **长线考量**：如果家庭成员使用频率变得极高，考虑平滑迁移至云服务器（如 Vultr/DigitalOcean 的基础套餐）或购买 Render 的 Starter 计划。

## 2. 核心架构缺陷：瞬时数据与长效存储的矛盾

### 2.1 痛点描述 (幽灵照片现象)
目前产品只做到了“营养素留存”，却丢失了“视觉留存”。
由于后端没有接入对象存储服务（OSS），前端在调用摄像头捕获图片后，仅仅是将其转换为冗长的 Base64 字符串丢给 Gemini 接口解析。解析一旦完成，照片的生命周期就彻底结束了。
这导致用户在 `HistoryList.jsx` 中只能看到冷冰冰的热量数字和“猪肉大葱包子”这几个字，却无法点开查看当时吃的那笼包子的真实模样。这不仅削弱了复盘的直观性，也让美好的家庭饮食分享失去了一半的乐趣。

### 2.2 下一步修复计划 (Sprint 2)
*   **引入云存储 (AWS S3 / Supabase Storage 等)**：
    *   在前端拿到图片后，首先将其上传至指定的 Bucket，并获取一个持久化的 CDN `imageUrl`。
    *   将该 `imageUrl` 随卡路里数据一起写入 PostgreSQL 的 `meals` 表中。
    *   在历史列表卡片中，渲染出精美的食物缩略图。这样不仅能用于自我回顾，更能让跨国聊天的长辈真实看到你在大洋彼岸吃的是什么，极大增强情感连接。

## 3. 边缘场景与可用性闭环

### 3.1 找回密码流程的缺失
*   **痛点**：目前 `Auth.jsx` 仅支持极其基础的注册与登录操作。如果家庭成员更换了设备且忘记了密码，当前系统将陷入彻底死局（只能联系管理员手动去 PG 数据库改字段）。
*   **修复计划**：
    *   引入基础的 SMTP 服务（如 SendGrid 或 Nodemailer 结合个人邮箱）。
    *   建立标准的“忘记密码 -> 发送包含 JWT 临时 Token 的重置邮件 -> 填写新密码”闭环。

### 3.2 占位的 ProPaywall
*   **状态**：目前的 `ProPaywall.jsx` 仅仅是一个前端壳子组件，并没有对接任何支付网关（如 Stripe 或微信支付），也没有实现后端对应的高级权限控制。
*   **迭代考量**：作为一个专注于开源与自部署的基础设施项目，该模块优先级最低。未来如果希望将其转变为一套可供他人订阅的 SaaS 模板，则需要在此处深度重构逻辑。
