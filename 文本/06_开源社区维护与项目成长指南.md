# 开源社区维护与项目成长指南

WeightHelper 采用 MIT 协议开源，这赋予了它极强的生命力。一个优秀的极客项目，其文档和社区生态与代码质量同等重要。本指南旨在梳理 WeightHelper 在 GitHub 上的最佳实践与成长路径。

## 1. 建立开发者友好的第一印象

`README.md` 和 `KNOWLEDGE_BASE.md` 是吸引其他开发者贡献代码的门面。目前的 README 已经具备了极好的底子，为了进一步破圈，我们需要：

*   **视觉冲击 (Hero Image / Demo)**：在 README 顶部放置一张清晰的架构图（展示双数据库自适应切换）或一段 5 秒的动态 GIF（演示如何拖动滑块瞬间重算卡路里）。
*   **一键部署徽章 (Deploy Buttons)**：由于应用已经完全兼容 Render 和 PostgreSQL，强烈建议在 README 中添加一个紫色的 `[Deploy to Render]` 按钮。只要准备好 `render.yaml` 蓝图文件，其他极客只需点击一下，填入自己的 `GEMINI_API_KEY`，就能在 3 分钟内拥有一个专属自己的家庭热量追踪器。
*   **双引擎架构的强调**：将“本地开发无需配置，克隆即跑（得益于 SQLite 回退机制）”作为亮点在 README 中加粗突出，这会极大降低新手的尝试门槛。

## 2. 规范化协作与 Issue 治理

当项目开始受到关注时，必须建立清晰的贡献管道。

### 2.1 任务标签化体系 (Labels)
在 GitHub 的 Issues 看板中，预先设置好几类核心标签，引导新人（Good First Issue）：
*   `enhancement: UI/UX`：例如将底部的模型显示优化得更不明显。
*   `bug: API`：追踪 Gemini 接口可能的格式变更或错误捕获漏斗。
*   `feature: storage`：例如接下来的 AWS S3 图像持久化接入任务。
*   `chore: chore`：例如完善忘记密码流程。

### 2.2 Pull Request (PR) 审查红线
作为这个家庭应用的核心维护者，任何外来的代码合并必须通过以下两道红线：
1.  **统一数据库适配器红线**：严禁任何试图在后端业务代码中手动拼接 `$1` 等针对特定数据库语法的 SQL 注入。所有操作必须经过封装好的 `dbRun` 和 `dbGet`。
2.  **前端包容性红线**：任何新增的前端功能，都不允许破坏极简操作流程（即不能增加新的必填项或复杂的深层级菜单），同时必须支持 `moment-timezone` 时区转化，不能出现硬编码本地时间的情况。

## 3. 项目发展的两种可能形态 (Forking Paths)

WeightHelper 作为一个极其优秀的起点，未来有两种截然不同的演进方向，可以根据社区的反馈来决定投入精力：

### 路径 A：纯粹的基础设施化 (The Self-Hosted Way)
*   完全放弃内置 `ProPaywall` 的商业化想法。
*   将其打造为类似 Nextcloud 或 Bitwarden 这样的极客私有云必装应用。
*   **核心动作**：封装标准的 Docker 镜像 (`docker-compose.yml`)，允许技术人员一键部署到自己的 NAS (Network Attached Storage) 或树莓派上。引入端侧大模型（如本地运行的 Ollama），彻底摆脱对 Google API 的依赖，实现绝对的数据私有和零网络延迟。

### 路径 B：轻量级的 SaaS 试水 (The Micro-SaaS Way)
*   将当前的单点系统升级为真正的多租户（Multi-tenant）架构。
*   **核心动作**：将目前的开源版本作为“社区版”长期免费维护。在此基础上分支出一个由你托管的“云端版”。接入真正的支付网关，用户不需要自己去申请什么 Gemini 密钥，直接扫码支付 10 元包月，开箱即用。主打“帮长辈省心”的孝心付费模式。
