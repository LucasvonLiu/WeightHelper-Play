# 真实用户画像与跨大洲使用场景分析

与追求海量下沉用户的泛商业化应用不同，WeightHelper 的设计初衷是为了解决特定场景下的高频痛点。其核心用户画像可以精准定位为一个**“分布在全球不同时区的极客家庭”**。

## 1. 核心用户画像与痛点

### 画像特征
*   **家庭结构**：全家成员关注健康，但由于工作或生活原因分布在不同国家（如北京、柏林、纽约、休斯敦）。
*   **技术认知**：至少有一位成员具备基础的 IT 部署能力（能够 Fork 代码、配置 API Key、在 Render 等平台拉起实例），愿意为全家人搭建专属基础设施。
*   **家庭成员痛点（非极客群体）**：对于长辈或其他非技术人员而言，传统的卡路里计算工具过于繁琐（需要搜名字、查数据库、填克数），他们极度抗拒这种高认知负荷的操作。

### 亟待解决的核心痛点
1.  **记录门槛高**：长辈或忙碌的家人没有耐心进行手动打字搜索。
2.  **多时区数据混乱**：当纽约的家人在当地时间晚上吃晚餐时，北京时间已经是第二天早上。如果使用普通应用，他们的晚餐可能会被错误地记录在北京时间的次日，导致所有人的热量缺口计算崩溃。
3.  **应用休眠与冷启动卡顿**：使用免费 PaaS（如 Render）托管的自建服务容易休眠，如果正好赶上饭点遭遇 50 秒的冷启动，将严重打击长辈的使用积极性。

## 2. 核心场景锚定与应对策略

### 场景一：无门槛的家庭用餐记录 (长辈友好)
*   **场景描述**：一位不太懂复杂电子设备的家庭成员在饭桌前，想要记录面前的一盘菜。
*   **应对设计**：
    *   **极简视觉入口**：摒弃复杂的表单，应用核心就是一个巨大的“拍照”按钮。
    *   **无需秤量的“模糊正确”**：利用 AI 自动识别种类和预估热量。更重要的是，通过极其直观的**滑动条（提供1/4份、半份等选项）**，让用户通过简单的视觉滑动来调整份量，彻底消灭了“克重输入”这道门槛。

### 场景二：跨大洲的异地打卡同步 (Chronobiological Integrity)
*   **场景描述**：身在休斯敦的家庭成员想要复盘自己一天的饮食，或者北京的家人想要查看远在柏林的成员今天有没有按时吃饭。
*   **应对设计**：
    *   **坚如磐石的绝对时间轴**：底层数据库严格按照 UTC 时间戳存储。
    *   **本地化时区渲染**：前端基于用户在设置中选择的时区（独立于设备所在时区，支持手动指定），利用 `moment-timezone` 将数据精确还原到其“当地的”日历格子中。
    *   **跨时区沟通辅助**：饮食记录条目的时间显示替换为世界时钟偏移格式（例如 `UTC+8 09:00`）。这样，当跨越半个地球的家人互相查看记录时，能清晰感知对方是在当地的什么时间进餐的，极大提升了亲情沟通的便利性。

### 场景三：遭遇免费 API 配额耗尽 (Disaster Recovery)
*   **场景描述**：作为开源自建项目，使用的 Google Gemini 免费 API 在频繁调用后触发了 `429 Too Many Requests`，或者当前请求的模型恰好下线 `404 Not Found`。
*   **应对设计**：
    *   **用户视角的无感降级**：用户不需要知道底层发生了什么，他们只需像往常一样拍照。
    *   **系统底层逻辑**：后台触发早已设计好的瀑布流模型灾备机制（`gemini-3.1-flash-lite` -> `gemini-3.5-flash` -> `gemini-3.0-flash` 等依次轮询重试）。系统自动接管故障，保证用户能顺利拿到结果。最多只会在下方低调显示当前成功调用的备用模型名称，维持一种“技术尽在掌握”的松弛感。
