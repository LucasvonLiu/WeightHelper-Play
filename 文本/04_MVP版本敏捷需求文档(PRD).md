# MVP 核心功能产品需求文档 (PRD)

## 1. 产品定位与目标
*   **产品名称**：WeightHelper (暂定)
*   **版本号**：v1.0 (MVP)
*   **核心目标**：验证“10秒内极速记录饮食”的核心价值，跑通“拍摄/语音 -> AI识别 -> 数据记录”闭环。
*   **不包含范围 (Out of Scope)**：社区动态、详细图文菜谱、运动跟练、商城导购。

---

## 2. 核心业务流程 (数据流向)

`用户端触发` -> `前端异步捕获` -> `后端API调度 (百度/阿里云)` -> `AI容错逻辑处理` -> `营养库映射` -> `结果入库与前端渲染`

---

## 3. 核心功能模块与用户故事 (User Stories)

### 3.1 极速记录模块 (核心)
> **User Story**: 作为一名需要控制体重的打工人，我希望能够用最短的时间（<10秒）记录我的饮食，以便我能轻松坚持这个习惯。

*   **功能点：视觉识别录入 (CV)**
    *   **业务逻辑**：
        1. 打开应用直接进入相机取景页。
        2. 用户点击拍摄，或从相册上传图片。
        3. 前端立即显示“正在为您计算热量...”的非阻塞提示，允许用户切出 App。
        4. 后端调用百度“菜品识别”API 获取识别结果及置信度。
    *   **性能要求**：图片上传及 API 返回的总感知时间（RTT）**必须低于 3.5 秒**。
*   **功能点：语音/自然语言录入 (NLP)**
    *   **业务逻辑**：
        1. 首页提供明显的麦克风按钮。
        2. 用户长按说话（如“半碗米饭加一份红烧肉”），前端调用原生语音转文字服务。
        3. 将文本发送给后台 LLM 进行结构化实体提取。

### 3.2 AI 容错与“人在回路”交互模块
> **User Story**: 作为用户，我知道 AI 有时候会认错食物或估不准重量。我希望当它不确定时，能让我以最省力的方式（比如滑动）去纠正它，而不是让我重新打字搜索。

*   **功能点：基于置信度的交互降级**
    *   **业务逻辑**：
        *   当 API 置信度 `> 85%`：直接入库记录，附带 `[AI确信]` 标签。
        *   当 API 置信度 `60% - 85%`：生成草稿。UI 底部弹窗展示识别出的主体（如“宫保鸡丁”），并提供横向滑动条：
            *   滑块左（偏少，预设 -30%）
            *   滑块中（标准份量，默认卡路里值）
            *   滑块右（吃撑了，预设 +40%）
            *   *规则*：用户拖动滑块时，上方热量数字实时变化。点击确认即保存。
        *   当 API 置信度 `< 60%` 或返回“非食物”：
            *   UI 提示：“这道菜太特别啦，AI 没看清。”
            *   提供 3 个系统猜测的热词 Tag 供快速选择，或者提供一个“呼叫 AI 伴侣手动补充”的快捷入口。

### 3.3 数据看板与时区逻辑 (底层防线)
> **User Story**: 作为用户，我希望我的日历数据是绝对准确的，无论我什么时候补记之前的饮食，都能被放在正确的日期里。

*   **功能点：抗脆弱的时间序列同步**
    *   **业务逻辑**：
        *   每条记录强制绑定两个时间戳：`实际进食时间 (Meal Time)` 和 `创建记录时间 (Creation Time)`。
        *   客户端强制获取设备本地时区（Timezone Offset），并随数据上报。
        *   若用户在夜间 00:30 补记昨天的“夜宵”，系统应默认将其归入“昨天”的日期面板，并弹窗提示：“已为您记录在昨日夜宵档”。
    *   **异常处理**：断网状态下，数据需存储在本地 SQLite/CoreData 中，网络恢复后优先基于 `Meal Time` 增量同步至云端，绝不允许发生记录覆盖或丢失。

### 3.4 情感伴侣模块 (留存钩子)
> **User Story**: 作为经常因为爆卡而感到沮丧的人，我希望这个 App 像一个懂我的朋友，在我吃多的时候鼓励我，而不是红彤彤地警告我。

*   **功能点：大模型驱动的情感化 Feedback**
    *   **业务逻辑**：
        *   每次完成记录（或一天结束时），系统基于当天的卡路里完成度，调用预设 prompt 的大模型接口生成一两句文案。
        *   **约束条件**：绝不能使用负面、指责性词汇（如“严重超标”、“禁止”）。
        *   *示例 (超标时)*：“哇塞，今天这顿大餐一定很解压！周末就是要开心一点嘛，明天多喝两杯水，我们继续加油！💧”

## 4. 依赖项与 API 成本评估

| 第三方服务 | 用途 | 成本与响应预估 | 替代方案 |
| :--- | :--- | :--- | :--- |
| **百度大脑 (菜品识别 API)** | 核心视觉识别 | 基础 QPS 10 够用，高并发单次成本微乎其微。国内延迟极低。 | 阿里云视觉开放平台 |
| **聚美智数/阿里云市场** | 食物卡路里热量数据库映射 | 低成本 JSON RESTful API，映射百度的菜品名称。 | 自建数据库（初期极不推荐，维护成本高） |
| **DeepSeek/通义千问 API** | NLP解析与情感伴侣文案生成 | 响应极快，Token 成本低，适合轻量级文本生成。 | 端侧小模型 (若考虑极致离线体验) |

---

## 5. 验收标准 (Acceptance Criteria)

1.  **极速达标**：在 4G/5G 网络下，从拍摄完毕到显示（或后台生成）卡路里结果，90% 的请求不超过 4 秒。
2.  **可用性底线**：置信度低于 60% 时，用户能在无需输入文字的前提下（仅靠滑动或点击推荐 Tag），在 5 秒内完成修正。
3.  **时间戳鲁棒性**：人为修改系统时间或跨时区测试时，本地与云端的历史日历数据不能发生位移和乱序。
